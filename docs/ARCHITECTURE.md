# Структура и данные

Это рекомендованная структура реализации. Сейчас существуют только `src/app`, `src/main.tsx`, конфигурация сборки и проверка подключения. Пустые функциональные модули заранее не создавались.

После [анализа существующих решений](research/open-source-crm.md) рекомендация сохраняется: собственное небольшое приложение на выбранном стеке. Atomic CRM используется как технический эталон, OpenProject — как ориентир правил переходов. Модель общего доступа к задачам и модель выполнения через `done_date` из Atomic не соответствуют нашим ограничениям; их не переносим. Агрегированная лента активности также не заменяет отдельную защищённую историю статусов.

```text
src/
  app/                   # Корневой компонент, маршруты, провайдер сессии, общие стили
  features/
    auth/                # Вход, выход, восстановление сессии
    objects/             # Список, карточка и формы объектов
    tasks/               # Карточка, формы, история, смена статуса, мои задачи
  shared/
    api/                 # Единственный клиент Supabase и сгенерированные типы базы
    ui/                  # Только действительно повторяющиеся элементы
supabase/
  migrations/            # Схема, ограничения, политики, функции и триггеры
tests/
  integration/           # API-тесты с реальными пользователями
docs/
scripts/
```

Компоненты экранов и запросы хранить в соответствующем функциональном модуле. Не вводить универсальные repository/service-слои заранее. React Context достаточно для сессии; локальное состояние подходит формам. При небольшом числе экранов допустимо обновлять данные после мутаций без отдельного серверного кэша.

## Таблицы

| Таблица | Основные данные |
| --- | --- |
| `profiles` | ID из `auth.users`, отображаемое имя, роль `manager` или `executor` |
| `objects` | ID, название, адрес, автор, дата создания, `deleted_at` |
| `tasks` | ID, название, описание, объект, исполнитель, статус, автор, дата создания, `deleted_at` |
| `task_status_history` | ID, задача, предыдущий и новый статус, действующий пользователь, время, комментарий |

Роль хранится в защищённой таблице, которую пользователь не может редактировать через API. Не доверять `user_metadata` для выдачи прав. `auth.users` использовать как штатный источник учётных записей, не копировать пароли в свои таблицы.

Статусы: `new`, `in_progress`, `in_review`, `accepted`, `rework`. Русские подписи находятся в UI; допустимые значения и переходы проверяет база.

## Контроль доступа

- Все таблицы приложения включают RLS. Неавторизованный пользователь не получает данные.
- Любой постановщик видит все объекты и задачи, а не только созданные им. Все постановщики имеют одинаковые права, как сказано в ТЗ.
- Исполнитель видит только назначенные ему задачи и связанные с ними объекты. В общей карточке объекта он также не должен увидеть чужие задачи.
- Смену статуса проверяет база: роль, текущее назначение, допустимая пара статусов и обязательный комментарий при возврате на доработку.
- Рекомендуемый механизм: RLS для доступа к строкам; BEFORE-триггер для переходов и запрета изменения исполнителем остальных полей; RPC `change_task_status` для передачи комментария и атомарной операции. Начать с наименьшего достаточного набора функций, проверить реальным API.
- Историю создаёт база в той же транзакции, что и изменение статуса, с `auth.uid()` и серверным временем. Клиент не передаёт автора или время записи истории. INSERT/UPDATE/DELETE истории закрыты для API-ролей; триггер записи имеет минимально необходимые права.
- При необходимости SECURITY DEFINER явно задавать пустой `search_path`, квалифицировать имена схем, ограничивать EXECUTE и проверять вызывающего пользователя. Не превращать функцию в обход RLS без проверок.
- При смене статуса и переназначении нужно исключить гонку двух пользователей: блокировать изменяемую строку в транзакции, не вычислять переход на основе устаревшего состояния клиента.

## Переназначение и удаление

Подтверждено работодателем: смена исполнителя не меняет статус, включая задачи в работе и принятые. Отдельный переход «В работе → В работе» не нужен. Статусная история при одном только переназначении не получает фиктивную запись о переходе.

Рекомендуемое следствие правила доступа: прежний исполнитель сразу теряет доступ, новый получает доступ и историю назначенной задачи. Если задача принята, она остаётся принятой; переходов из принятого состояния в ТЗ нет. Если задача на проверке, новый исполнитель ждёт решения постановщика. Это следствия таблицы переходов, а не новые согласованные требования.

Удаление выполнить логически через `deleted_at`: исчезает из обычных списков, история сохраняется. Удаление объекта должно логически удалить его активные задачи в одной транзакции, сохраняя историю. Это выбранное допущение реализации, не отдельное уточнение работодателя. Физические CASCADE-удаления истории не использовать. Интерфейс восстановления не входит в ТЗ.

## Публикация

Сборка Vite — статический `dist`. Для будущего размещения на Vercel нужны build command `npm run build`, output directory `dist`, Node 24 и две публичные переменные из `.env.example`. Для BrowserRouter настроить возврат `index.html` для клиентских маршрутов. Доступы тестовых пользователей передавать работодателю отдельно от исходников и публичного README.

В этой подготовке Vercel не настраивался и приложение не публиковалось.
