# Архитектура 2CRM

Приложение состоит из статического React-клиента и Supabase. Клиент использует Auth для входа, читает Data API и вызывает пять функций записи. Источник ролей находится в защищённой таблице profiles, а не в редактируемом user_metadata.

## Структура

- src/app: маршруты, провайдеры, навигация и стили.
- src/features/auth: вход, выход и восстановление сессии.
- src/features/objects: список, карточка и форма объекта.
- src/features/tasks: мои задачи, карточка, формы и история.
- src/shared/api: клиент Supabase, типы из базы и ограничение ожидания HTTP.
- src/shared/ui: повторяющиеся состояния, формы с защитой изменений и подтверждение удаления.
- supabase/migrations: воспроизводимая SQL-схема и права.
- tests/integration: проверки настоящего API с разными пользователями.
- tests/unit: ожидание запроса через локальный HTTP-сервер и представление шкалы статусов.

React Router использует Data Router для маршрутизации и блокировки ухода с изменённой формы. Данные экранов обновляются после мутаций и при возвращении фокуса. Отдельного серверного кэша и realtime-подписки нет. Запрос ограничен 15 секундами; ошибка оставляет кнопку повтора и введённые поля.

## Данные

| Таблица | Назначение |
| --- | --- |
| profiles | UUID из auth.users, отображаемое имя и роль manager/executor |
| objects | Название, адрес, автор, серверные даты, версия и deleted_at |
| tasks | Название, описание, объект, исполнитель, статус, автор, даты, версия и deleted_at |
| task_status_history | Задача, откуда/куда, пользователь, снимок имени, серверное время и комментарий |

Внешние ключи истории не используют каскадное удаление. Пользовательский API не получает INSERT/UPDATE/DELETE на таблицы приложения. RLS включён на всех четырёх таблицах. Индексы поддерживают внешние ключи, выборку активных записей и историю задачи.

## Чтение

Постановщик видит все активные объекты и задачи независимо от автора. Исполнитель видит только назначенные ему активные задачи и содержащие их объекты. В общей карточке объекта чужие задачи также отфильтрованы RLS.

Имена и роли профилей доступны пользователям с назначенной ролью, чтобы показывать исполнителей и авторов. Пароли и email в profiles не копируются. Менять профили через пользовательский Data API нельзя.

История доступна постановщику, а исполнителю только для текущей доступной задачи. Переназначение сразу меняет право чтения истории. Сохранённая история удалённой задачи остаётся в базе доступной постановщику через API; отдельный архив в интерфейсе не входит в ТЗ.

## Запись

Публичные функции save_object, save_task, change_task_status, delete_task и delete_object работают как SECURITY INVOKER-обёртки. Привилегированная реализация находится в неэкспонируемой схеме private. EXECUTE выдан только authenticated; права PUBLIC/anon отозваны. Каждая внутренняя функция проверяет auth.uid(), роль и доступ к записи. Имена схем квалифицированы, search_path пустой.

Весь пользовательский путь записи проходит через пять функций. Отдельного триггера для повторения тех же ограничений нет.

Функция смены статуса блокирует строку задачи, сверяет версию и допустимую пару статусов, проверяет роль/назначение и наличие комментария доработки. private.has_non_whitespace отвергает null и значения только из Unicode-пробелов; тот же предикат защищает CHECK истории. Изменение и запись истории выполняются в одной транзакции. Автор и время истории формируются сервером.

Открытая форма при конфликте хранит черновик отдельно от показанной актуальной версии. Продолжение требует явного выбора пользователя; каждая попытка записи всё равно проверяет версию в базе. Создание, редактирование и удаление также сверяют версию. Один из двух одновременных переходов проходит, другой получает конфликт. Создание и перенос задачи блокируют связанные объекты в стабильном порядке. Удаление объекта блокирует его строку, проверяет версию и число активных задач, затем логически удаляет объект и задачи атомарно.

## Статусы и переназначение

Допустимы создание → new, new → in_progress, in_progress → in_review, in_review → accepted/rework, rework → in_progress. Назначенный исполнитель выполняет переходы начала и отправки; постановщик принимает и возвращает. Остальные переходы отклоняет база.

Смена исполнителя не меняет статус, включая in_progress и accepted. Фиктивная запись перехода при переназначении не создаётся. В принятом состоянии дальнейших переходов нет, как задано таблицей ТЗ.

## Границы защиты

Серверный ключ используется только локальными административными скриптами и фикстурами тестов. Он не нужен сборке и не входит в VITE_* или Git. Supabase Admin API остаётся доверенным административным каналом: владелец инфраструктуры технически может менять данные, поэтому неизменяемость истории относится к пользовательским ролям и API.
